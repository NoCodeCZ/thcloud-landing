จุดล้มเหลวที่ 1: เริ่มต้นจาก Interface ก่อน

ข้อผิดพลาดที่พบบ่อยที่สุดคือการซื้อ AI Tool — Chatbot, Dashboard Assistant, Report Generator — ก่อนที่ข้อมูลข้างใต้จะสะอาด รวมเป็นหนึ่ง และเข้าถึงได้ Tool นั้นทำงานได้ดีในการ Demo แต่ล้มเหลวในการใช้งานจริง เพราะมันดึงข้อมูลที่ไม่ครบหรือล้าสมัย

⚠ ข้อผิดพลาดที่พบบ่อย

การนำ AI Assistant ไป Deploy บนข้อมูลที่กระจัดกระจายไม่ได้แก้ปัญหาความกระจัดกระจาย แต่กลับเปิดโปงมัน — และเปิดโปงในช่วงเวลาที่แย่ที่สุด เช่น ตอนที่ลูกค้าหรือผู้บริหารกำลังรอคำตอบ

ลำดับที่ถูกต้องคือเสมอ: Data Foundation ก่อน → Intelligence Layer ถัดมา → AI Interface เป็นสุดท้าย คู่มือนี้เรียงลำดับตามนั้นทุกประการ

จุดล้มเหลวที่ 2: รวมข้อมูลโดยไม่ Normalise

การย้ายข้อมูลทั้งหมดมาไว้ในที่เดียวไม่ได้หมายความว่าคุณมีข้อมูลที่รวมเป็นหนึ่งแล้ว ถ้าข้อมูล Facebook Ads เรียก Conversion ว่า 'Results' แต่ข้อมูล Shopee เรียกว่า 'Orders' และข้อมูล LINE เรียกว่า 'Confirmations' คุณก็แค่มี Warehouse เดียวที่เต็มไปด้วยข้อมูลที่เปรียบเทียบกันไม่ได้

การ Normalise ข้อมูล — ตกลงกันให้ได้ถึง Vocabulary, Schema และ Grain ที่สอดคล้องกันก่อนนำเข้า — คืองานที่มองไม่เห็นซึ่งกำหนดว่า Warehouse ของคุณจะเป็นทรัพย์สินหรือหนี้สิน ภาค 1 ของคู่มือนี้ครอบคลุมเรื่องนี้โดยละเอียด

เมื่อสร้าง Data Infrastructure มักจะเกิดแรงจูงใจให้สร้างรองรับทุก Use Case ที่อาจเกิดขึ้นในอนาคต ผลที่ได้คือ Pipeline ที่ซับซ้อนเกินไปจนดูแลไม่ได้ Schema ที่นามธรรมเกินไปจน Query ลำบาก และ Dashboard ที่ไม่มีใครใช้เพราะตอบคำถามที่ไม่มีใครถาม

✓ แนวทางที่ดีที่สุด

จุดล้มเหลวที่ 4: มอง AI เป็น Product ไม่ใช่ Layer

AI Tool อย่าง ChatGPT, Claude, Gemini คือ Interface ไม่ใช่ Intelligence ตัว Intelligence มาจากการเชื่อมต่อ Interface เหล่านั้นกับข้อมูลที่ถูกต้อง ทันสมัย และมีโครงสร้าง Language Model ที่ไม่รู้จักธุรกิจของคุณจะให้คำตอบทั่วๆ ไป แต่ Model เดียวกันที่เชื่อมต่อกับ Warehouse, Dashboard และประวัติลูกค้าของคุณจะกลายเป็นเครื่องมือดำเนินงานจริงได้

ความแตกต่างนี้คือสมมติฐานหลักของคู่มือทั้งฉบับ เราไม่ได้สร้าง AI Product เราสร้าง Infrastructure Layer ที่ทำให้ AI มีประโยชน์จริงสำหรับธุรกิจของคุณ

ขั้นตอนที่ 2 — ออกแบบ Schema ก่อน Ingest

Schema ของ Warehouse คือ Vocabulary ที่ทั้งธุรกิจจะใช้พูดถึงข้อมูล เปลี่ยนทีหลังแล้วคุณต้องเปลี่ยน Dashboard ทุกอัน Query ทุกตัว และ AI Agent ทุกตัวที่พึ่งพามัน ลงทุนเวลาตรงนี้ก่อนที่การ Ingest จะเริ่ม

Warehouse ที่มีโครงสร้างดีใช้ตาราง 3 ชั้น แต่ละชั้นมีจุดประสงค์ต่างกัน:

ชั้น

สิ่งที่เก็บ

ออกแบบ Entity หลักก่อน

ธุรกิจ E-Commerce หลายช่องทางทุกแห่งมี Entity หลัก 5 ตัวเหมือนกัน ออกแบบตารางเหล่านี้ก่อนสัมผัส Platform-specific Data:

  • Orders — ทุก Transaction จากทุกช่องทางในตารางเดียว Columns: order_id, channel, platform, date, customer_id, gross_revenue, net_revenue, discount_applied, status
  • Products — Master SKU Columns: sku_id, product_name, category, subcategory, unit_cost, retail_price
  • Customers — หนึ่ง Row ต่อลูกค้าหนึ่งคน ข้ามทุกช่องทาง Columns: customer_id, acquisition_channel, first_order_date, lifetime_value, segment
  • Ad Spend — ทุก Record ค่าโฆษณา Columns: date, platform, campaign_id, ad_set_id, spend, impressions, clicks, conversions
  • Events — ทุกอย่างที่เป็น Time-series ที่ไม่เข้าพวกข้างต้น เช่น Chat Message, การเคลื่อนไหว Inventory

การตัดสินใจสำคัญ

กำหนดกลยุทธ์ Primary Key ก่อน Ingest ลูกค้าที่ซื้อบน Shopee และ Chat บน LINE คือคนเดียวกัน customer_id ของคุณต้องมีกลยุทธ์ — ไม่ว่าจะเป็น Identifier ร่วม (เบอร์โทร, อีเมล) หรือ Matching Algorithm — ไม่เช่นนั้นคุณจะนับพวกเขาเป็น 2 คนตลอดไป

Grain: แนวคิดที่สำคัญที่สุดใน Schema Design

Grain คือระดับรายละเอียดที่ Fact Table เก็บข้อมูล ถ้าตาราง Orders เก็บหนึ่ง Row ต่อหนึ่งคำสั่งซื้อ Grain คือระดับ Order-level ถ้าเก็บหนึ่ง Row ต่อหนึ่ง SKU ต่อหนึ่งคำสั่งซื้อ (Order Lines) Grain คือระดับ Order-line

ห้ามผสม Grain ในตารางเดียวกัน การ Aggregate ตาราง Row-per-order กับตาราง Row-per-order-line จะทำให้นับซ้ำ — เป็น Bug ที่พบบ่อยที่สุดและหาสาเหตุยากที่สุดใน Commerce Warehouse

✓ แนวทางที่ดีที่สุด

กำหนด Grain อย่างชัดเจนสำหรับทุก Fact Table ก่อนสร้าง เขียนเป็น Comment ใน Table DDL: -- Grain: one row per order, per channel, per day.

Incremental vs Full Refresh — รู้ความแตกต่าง

ทุก Sync Job มีกลยุทธ์: Incremental (Sync เฉพาะ Record ใหม่และที่เปลี่ยน) หรือ Full Refresh (Sync ทุกอย่างใหม่ทุกครั้ง)

Full Refresh ง่ายต่อการ Implement แต่แพงเมื่อ Scale ขึ้น Ad Account ที่มีประวัติ 3 ปีมีข้อมูลหลายสิบล้าน Row การ Resync รายวันใช้ Compute มากและเสี่ยงถูก Rate Limit โดย API

⚠ ข้อผิดพลาดที่พบบ่อย

ขั้นตอนที่ 4 — สร้าง Data Quality Check ตั้งแต่แรก

คุณภาพข้อมูลไม่ใช่เรื่องที่ต้องคิดทีหลัง ทันทีที่ AI Agent บอกสมาชิกทีมอย่างมั่นใจว่ารายได้คือ 2.3 ล้านบาท ในขณะที่ตัวเลขจริงคือ 1.8 ล้านบาทเพราะ Sync ล้มเหลวเงียบๆ เมื่อ 3 วันก่อน ความเชื่อถือในระบบทั้งหมดจะพังทลาย

สร้าง Check 4 อย่างนี้ใน Pipeline ทุกตัวก่อนที่ Dashboard ใดๆ จะ Query ข้อมูล:

1. Row Count Validation

หลังทุก Sync เปรียบเทียบจำนวน Row ของข้อมูลที่โหลดใหม่กับช่วงที่คาดหวังตาม Average ประวัติ Sync ที่ Load ศูนย์ Row หรือ 10 เท่าของปกติคือสัญญาณ ไม่ใช่ผลลัพธ์

2. Null Check บน Column ที่สำคัญ

กำหนด Column ที่ห้าม Null เด็ดขาด เช่น order_id, date, platform, gross_revenue และแจ้งเตือนเมื่อพบ order_id ที่เป็น Null หมายความว่า Record นั้น Join กับอะไรไม่ได้เลย มันคือหนี้สินที่มองไม่เห็น

        

3. Revenue Reconciliation

ทุกวัน: รวม orders table ใน Warehouse ของวันก่อน เปรียบเทียบกับตัวเลขที่ Platform รายงาน ถ้าต่างกันเกิน 2% ให้ทำ Manual Review นี่คือ Check ที่สำคัญที่สุดที่คุณจะสร้าง

4. Freshness Monitoring

บันทึก Timestamp ล่าสุดของ updated_at หลังทุก Sync แจ้งเตือนถ้า Timestamp ล่าสุดล้าหลังวันที่คาดหวังเกิน 1 รอบ Data Warehouse ที่หยุดอัปเดตเงียบๆ แย่กว่าอันที่ไม่เคยมีเลย — ทีมตัดสินใจบนตัวเลขเก่าโดยไม่รู้ตัว

RAG ทำงานอย่างไร — และล้มเหลวที่ไหน

RAG คือรูปแบบการทำให้ AI รู้จักเอกสาร Conversation และความรู้ที่ไม่ได้อยู่ใน Training Data นี่คือกระบวนการจริง:

  1. นำเอกสารต้นทาง (รายละเอียดสินค้า, ประวัติ Chat, นโยบาย, FAQ)
  2. แบ่งเป็นส่วนๆ ประมาณ 200–500 Token ต่อส่วน
  3. ส่งแต่ละส่วนผ่าน Embedding Model ที่แปลงเป็น Vector — ตัวเลขชุดหนึ่งที่แทน Semantic Meaning
  4. เก็บ Vector เหล่านี้ใน Vector Database (pgvector ในระบบนี้)
  5. เมื่อ Query มาถึง ให้ Embed Query ด้วย Model เดียวกัน
  6. ค้นหา Vector Database สำหรับส่วนที่ Vector ใกล้เคียงกับ Query Vector มากที่สุด (Cosine Similarity)
  7. ใส่ส่วนที่ Match ดีที่สุด Top-k เข้าไปใน Prompt เป็น Context
  8. Model สร้างคำตอบโดยอิงจาก Context นั้น

⚠ ข้อผิดพลาดที่พบบ่อย

RAG ล้มเหลวเมื่อ Chunk ใหญ่เกินไป (ประโยคที่เกี่ยวข้องถูกฝังอยู่ใน Chunk 2,000 คำที่ Match บางส่วนเท่านั้น) เมื่อ Embedding Model จัดการภาษาไทยได้ไม่ดี หรือเมื่อข้อมูลที่เกี่ยวข้องไม่มีใน Knowledge Base เลย ความล้มเหลวเหล่านี้ไม่ชัดเจน — Model จะยังสร้างคำตอบที่ฟังดูมั่นใจออกมา

การออกแบบ RAG เชิงปฏิบัติสำหรับ Commerce ในไทย

Chat LINE คือแหล่งข้อมูล Intent ของลูกค้าที่สมบูรณ์ที่สุดสำหรับแบรนด์ Commerce ในไทย — และยากที่สุดในการจัดโครงสร้างสำหรับ RAG

การตัดสินใจออกแบบที่สำคัญ:

  • แบ่ง Chunk ระดับ Conversation ไม่ใช่ระดับข้อความ — ข้อความเดี่ยว ('ราคาเท่าไหร่') ไม่มี Context Thread ของ Conversation รอบข้างมี
  • แท็ก Chunk ด้วย Metadata ตอน Index: customer_id, วันที่, product_category_mentioned, intent_signal (สอบถาม/ร้องเรียน/สั่งซื้อ/กลับมาซื้อซ้ำ) — ช่วยให้ Filter ก่อน Semantic Search ซึ่งเพิ่ม Precision อย่างมาก
  • ใช้ Embedding Model ที่รองรับภาษาไทย — text-embedding-3-large จาก OpenAI รองรับภาษาไทยได้ดีพอ Model หลายภาษาของ OpenAI ดีกว่า Model ภาษาอังกฤษเดียวสำหรับข้อความไทย
  • อย่า Embed ข้อความ Broadcast โปรโมชั่น — พวกมันเป็น Noise ใน Intent Search Index

Tool Use — Agent Query ข้อมูล Dashboard อย่างไร

Tool Use คือวิธีที่ AI Agent เรียก Dashboard และรับข้อมูล Real-time Agent ไม่ 'เห็น' Dashboard Metabase ของคุณโดยตรง — คุณต้องเปิดเผยข้อมูลเป็น Function ที่ Model เรียกได้

นี่คือรูปแบบ:

  1. คุณเขียน Python Function: get_daily_revenue(date, channel=None) → คืนค่า Dict ของตัวเลขรายได้จาก ClickHouse
  2. ลงทะเบียน Function นี้เป็น 'Tool' ใน LangChain พร้อมชื่อ คำอธิบาย และ Parameter Schema
  3. บอก Language Model ว่ามี Tool นี้และทำอะไร
  4. เมื่อ User ถาม 'ยอดขายเมื่อวานแยกตาม Category เป็นเท่าไหร่?' Model ตัดสินใจเรียก get_daily_revenue(date='yesterday')
  5. Code ของคุณ Execute SQL Query กับ ClickHouse และคืนผลลัพธ์
  6. Model รับผลลัพธ์และเรียบเรียงคำตอบเป็นภาษาธรรมชาติ

ความหมายในทางปฏิบัติ

คุณภาพคำตอบของ Agent ถูกกำหนดโดยตรงจากคุณภาพ SQL Query ที่อยู่ข้างใต้ ถ้าตาราง mart_daily_revenue มี Grain ที่ถูกต้องและ Join ที่ถูกต้อง คำตอบของ Agent จะแม่นยำ ถ้าตารางมีการนับซ้ำหรือข้อมูลล้าสมัย Agent จะทำซ้ำข้อผิดพลาดเหล่านั้นอย่างมั่นใจ

AI Interface: Open WebUI

Open WebUI คือทางเลือก Self-hosted ที่มีฟีเจอร์ครบสำหรับ ChatGPT Team จุดต่างหลักคือ Route ไปยัง LLM Provider ใดก็ได้ผ่าน Interface เดียว ทีมไม่ถูกล็อคกับ Model เดียวและไม่ต้องมี Subscription หลายอัน

สิ่งที่ต้องระวัง: Open WebUI เป็นโปรเจกต์ Open Source ที่พัฒนาเร็ว UI เปลี่ยนแปลงมากระหว่างเวอร์ชัน ล็อค Docker Image Version ใน Production และทดสอบ Upgrade ใน Staging ก่อน Deploy

Model Router: LiteLLM

LiteLLM แปล API ของ LLM Provider ทุกรายเป็น Endpoint OpenAI-compatible เดียว Agent, Tool Call, Prompt ทุกอย่างผ่าน LiteLLM ซึ่งหมายความว่าคุณได้ Cost Tracking, Fallback Routing, Caching และ Budget Control ในที่เดียว

⚠ ข้อผิดพลาดที่พบบ่อย

Budget Control ของ LiteLLM ตั้งได้ต่อ Model และต่อ Team ไม่ใช่ต่อ User ถ้าต้องการ Cost Attribution ระดับ User ต้องสร้าง Logging Layer เพิ่มเติม อย่าสมมติว่า Reporting ที่มีมาพร้อมครอบคลุมทุก Use Case การเรียกเก็บเงิน

Implementation Playbook

แผนการสร้างรายเฟส · Failure Mode · ความต้องการทีม

การสร้าง: รายเฟส

นี่คือลำดับที่ได้ผลสม่ำเสมอ หลักการที่สำคัญที่สุด: อย่าเริ่มเฟสใหม่จนกว่าเฟสปัจจุบันจะ Validate แล้ว การข้ามการ Validate คือสาเหตุที่พบบ่อยที่สุดที่ทำให้โปรเจกต์ต้อง Rebuild อย่างแพง

เฟส 1 — สถาปัตยกรรมข้อมูลและ Audit (สัปดาห์ 1–2)

ผลงาน: เอกสารสถาปัตยกรรมข้อมูลที่ได้รับอนุมัติก่อนสร้าง Infrastructure ใดๆ

เฟสนี้ผลิต 3 Output:

  • รายการแหล่งข้อมูล — ทุก Platform ประเภทการเชื่อมต่อ ข้อมูลที่มี เจ้าของ และช่องว่างปัจจุบัน
  • การออกแบบ Warehouse Schema — คำนิยาม Entity, การตัดสินใจ Grain, ชื่อ Column, กลยุทธ์ Primary Key
  • แผน Ingestion — แหล่งไหน API อัตโนมัติ แหล่งไหน Scheduled Export แหล่งไหน Manual และความถี่เท่าไหร่

⚠ ข้อผิดพลาดที่พบบ่อย

ความล้มเหลวในเฟส 1 ที่พบบ่อยที่สุด: ข้ามการออกแบบ Schema และไปเชื่อมต่อแหล่งข้อมูลโดยตรง คุณจะมีข้อมูลใน Warehouse ภายในไม่กี่วัน — แล้วใช้เวลา 3 เดือนถัดมา Restructure เพราะ Grain ผิดหรือ Naming ไม่สอดคล้อง

Gate เฟส 1: สมาชิกทีมทุกคนที่จะใช้ Dashboard ตรวจสอบ Schema และยืนยันว่าตรงกับวิธีที่พวกเขาคิดเกี่ยวกับธุรกิจ ถ้าคนการเงินและคนการตลาดนิยาม 'รายได้' ต่างกัน ต้องแก้ในเฟส 1 ไม่ใช่ค้นพบในเฟส 4 เมื่อ Dashboard ของพวกเขาไม่ตรงกัน

เฟส 2 — ตั้งค่า Infrastructure และ Ingestion (สัปดาห์ 2–4)

ผลงาน: ทุก Service ทำงาน Pipeline Ingestion อัตโนมัติทั้งหมด Active ข้อมูลไหลเข้า Raw Layer

  1. Provision เซิร์ฟเวอร์หรือ Cloud Environment — ขนาด Compute ตาม ClickHouse Analytical Query Volume ไม่ใช่ Operational DB Load
  2. Deploy Service ใน Docker — ClickHouse, Supabase, Airbyte, Open WebUI, LiteLLM, Metabase, Directus
  3. Configure Network: Service ที่ Internal ไม่ Expose ออกภายนอก Service ที่ External อยู่หลัง Authentication
  4. ตั้งค่า Airbyte Connector — Facebook Ads ก่อน (คุณภาพ Connector ดีที่สุด) แล้วค่อย Shopee, Lazada
  5. Validate แต่ละ Connector: รัน Sync แรก เช็คจำนวน Row ตรวจสอบ Schema Mapping
  6. สร้าง CSV Import Template สำหรับ TikTok Shop และ Google Ads — ทดสอบกับไฟล์ Export จริง

⚠ ข้อผิดพลาดที่พบบ่อย

อย่าใส่ API Credential (API Key, OAuth Token) ของ Airbyte ใน Environment File เป็น Plain Text ใช้ Secrets Manager API Token ของ Facebook Ads ที่หลุดออกไปคือความรับผิดทางธุรกิจ

Gate เฟส 2: รัน Revenue Reconciliation Check (ภาค 1 ขั้นตอนที่ 4) ยอดรวมใน Warehouse สำหรับ 30 วันที่ผ่านมาควรตรงกับรายได้ที่ Platform รายงานภายใน 2% ถ้าไม่ตรง หาช่องว่างก่อนสร้าง Dashboard บนนั้น

เฟส 3 — Transformation และ Data Mart Build (สัปดาห์ 4–6)

ผลงาน: Staged และ Mart Table ที่ Populate แล้ว Metric ธุรกิจหลักที่คำนวณได้จาก SQL

  1. Staging Table — ทำความสะอาดและ Normalise แต่ละแหล่ง: Format วันที่, สกุลเงิน, Status Code, ชื่อสินค้าให้มาตรฐาน
  2. Core Entity Table — mart_customers, mart_products, mart_orders (รวมจากทุกช่องทาง)
  3. Attribution และ Join Table — เชื่อม ad_spend กับ orders ผ่าน Attribution Window Logic
  4. Aggregation Table — mart_daily_revenue, mart_campaign_performance, mart_sku_performance
  5. ML/Predictive Table (MindsDB) — Customer Churn Score, Sales Forecast — มาสุดท้ายหลัง Aggregation Stable

✓ แนวทางที่ดีที่สุด

ใช้ dbt (data build tool) สำหรับ Transformation Logic มัน Compile SQL ติดตาม Dependency ระหว่าง Model รัน Test และสร้าง Documentation อัตโนมัติ เป็นมาตรฐาน Industry สำหรับ Warehouse Transformation ด้วยเหตุผลที่ดี และ Integrate กับ ClickHouse และ PostgreSQL โดยตรง

Gate เฟส 3: Stakeholder ที่ไม่เคยสัมผัสข้อมูลสามารถถามคำถามธุรกิจจริง 5 ข้อและได้คำตอบที่ถูกต้องโดยเขียน SQL กับ Mart Table ถ้าทำไม่ได้ Mart ยังไม่พร้อมสำหรับ Dashboard

เฟส 4 — Dashboard Build และ Review (สัปดาห์ 6–8)

ผลงาน: Marketing, Sales และ Operations Dashboard ที่ Live, Review และ Sign Off โดยแต่ละทีมแล้ว

สร้างทีละ Dashboard เริ่มจาก Sales เพราะมีเส้นทาง Validation ตรงที่สุด (เปรียบเทียบกับคำสั่งซื้อใน Shopee Admin ตัวเลขควรตรงกัน) แล้วไปที่ Marketing จากนั้น Operations

สำหรับแต่ละ Dashboard:

  1. ร่าง Layout บนกระดาษก่อน — ลิสต์ทุก Metric, ทุก Chart Type, ทุก Filter ที่ต้องการ
  2. สร้างใน Metabase เริ่มจาก Metric ที่สำคัญที่สุด
  3. Review กับ User หลัก — ไม่ใช่ 'ดูถูกไหม?' แต่เป็น 'เปลี่ยนวิธีทำงานของคุณไหม?'
  4. Reconcile Metric อย่างน้อย 3 อันกับ Source-of-truth (Platform Report หรือ Spreadsheet) ก่อน Sign Off
  5. ตั้งค่า Alert และ Subscription

⚠ ข้อผิดพลาดที่พบบ่อย

ความล้มเหลวในเฟส 4 ที่พบบ่อยที่สุด: สร้าง Dashboard ที่ดูถูกต้องแต่ผิดเล็กน้อย Chart รายได้ที่แสดง 2.3 ล้านบาทในขณะที่จริงๆ คือ 2.1 ล้านบาทจะไม่ถูกจับด้วยการดูเฉยๆ สร้าง Reconciliation Check รันมัน ทุกครั้ง

เฟส 5 — AI Agent Deployment (สัปดาห์ 8–10)

ผลงาน: Sales Agent และ Customer Intent Agent ที่ Deploy แล้ว ทดสอบกับ Query จริง เข้าถึงได้ผ่าน Open WebUI

  1. กำหนด Scope ของ Agent: ตอบคำถามอะไร ต้องการข้อมูลอะไร จะปฏิเสธตอบอะไร?
  2. เขียน Tool Function และทดสอบ Independent กับ Mart Table
  3. สร้าง Prompt — รวม Role, Scope, Tool ที่มี, Format Output และคำสั่งเมื่อล้มเหลว
  4. รัน Adversarial Test — ถามคำถามที่ Agent ไม่ควรรู้, ถามคำถามคลุมเครือ, ขอข้อมูลที่แต่งขึ้น
  5. เปรียบเทียบคำตอบของ Agent กับค่า Dashboard สำหรับช่วงเวลาเดียวกัน — ควรตรงกัน
  6. Deploy ไปยัง Open WebUI เป็น Workspace ที่ทีมที่เกี่ยวข้องเข้าถึงได้

การจัดการ Hallucination

คำสั่งที่สำคัญที่สุดใน Prompt ของ Business Agent ใดๆ: 'ถ้าข้อมูลไม่มีคำตอบ ให้บอกชัดเจน อย่าประมาณหรืออนุมานค่าที่ควรมาจากข้อมูล' Agent ที่บอกว่า 'ไม่มีข้อมูลนี้' น่าเชื่อถือ Agent ที่แต่งตัวเลขที่ฟังดูสมเหตุสมผลออกมาอันตราย

Gate เฟส 5: สมาชิกทีม 3 คนใช้ Agent อิสระกัน 1 สัปดาห์ พวกเขา Verify คำตอบอย่างน้อย 5 ข้อต่อวันกับ Dashboard ความไม่ตรงกันใดๆ ถูก Log และแก้ไขก่อนที่ Agent จะถือว่า Production-ready

แบบฟอร์มที่ 1 — Data Source Audit

คำถามที่ต้องตอบก่อนกรอกแบบฟอร์ม:

  • คุณมี API Access สำหรับ Platform นี้ไหม? (ตรวจสอบว่ามี Credential/Developer Access)
  • ข้อมูลมีผ่าน Export ไหม? ที่ Granularity อะไร — ระดับ Order, Daily Summary หรือแค่ Monthly?
  • ข้อมูล Historical ย้อนหลังได้ไกลแค่ไหน? (กำหนดว่า Initial Load จะใช้เวลานานแค่ไหน)
  • มี Rate Limit บน API ที่จะกระทบความถี่ Sync ไหม?

แบบฟอร์มที่ 2 — KPI Prioritisation

วิธีใช้: สำหรับแต่ละทีม ลิสต์ 5 การตัดสินใจรายวันของพวกเขา แล้ว Map Metric ที่ขับการตัดสินใจแต่ละอัน ถ้าหา Metric ให้การตัดสินใจไม่ได้ นั่นคือคำถามเชิงกลยุทธ์ (นอก Scope ของ Dashboard) หรือช่องว่างข้อมูลที่ต้องเติม
